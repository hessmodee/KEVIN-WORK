# Kevin recovery decision rules v1

Purpose: retain lessons from real failures and choose the next bounded, evidence-backed step. This document is a learning artifact, not executable authority or proof that Kevin has mastered the procedure.

## Start with the actual failure

Separate service health, runtime errors, semantic acceptance, evidence completeness and owner outcomes. A healthy Gateway, exit code 0 or Benchmark30/30 does not prove an agent complied with its task.

The September 2 main-canary incident had a 127-character final output whose SHA256 was 3C9BD342FA050017F16FF421A1288D97BE4F116174831E0A55A351C336112B4B. That exactly matches the reviewed OpenClaw context-overflow banner. Classify that fingerprint as a runtime-overflow signature; do not infer the underlying context setting from the message alone.

Before another attempt, obtain the effective main model/provider/context and reserve budgets, bootstrap/skills/tools sizes, actual loaded Ollama context, structured runtime error, and existing request/session/transcript correlation. A model alias containing 16k is not a measured context window. Preserve the original failure and exact-response acceptance.

## Unknown evidence stays unknown

An incomplete transcript with zero observed tool events does not prove a complete zero-tool turn. Absent or null tool inventory is different from an explicit empty inventory. Stale data and missing data must not become healthy zeroes.

Require one matching user event, correlated session identity, terminal assistant completion, exact case-sensitive response and verified zero tool calls for the isolated main canary. Do not trim an error into a pass or substitute Benchmark health for task success.

## Protect learned skills

The composite-skill registry is Kevin's record of proven reusable procedures. A malformed, unreadable, oversized, duplicate or unsupported registry must block Skill Lab advancement while preserving the original bytes and existing work queues. A missing registry with prior completed-skill receipts must also block; never invent empty history.

A registry fault does not authorize deletion, guessed reconstruction, unverified backup restoration or another execution of an already-proven skill. Recover from authenticated prior evidence through a separately qualified repair. Record the fault and continue an independent GREEN lane when available.

For an intact registry, the same skill ID, version and manifest must reuse existing proof without duplicate primitive actions. The same ID/version with different content must be rejected as a collision. A new filename or version number does not replenish a failed repair's attempt budget.

## Execute and verify within the existing boundary

Use only owner-approved typed operations or existing proven GREEN primitives. Check ownership, queue state, source identity, resource limits, idempotency and rollback before a production change. Keep one production/proof crossing and preserve local-only credentials and private transcripts.

Record the observed failure, source/evidence identities, hypothesis, action, attempts, independent postcondition, result and next state. If the same repair family reaches its limit, preserve BLOCKED/COOLING history and change approach only when material new evidence or owner direction permits it.

Open the actual KEVIN-TURNOVER-LATEST first when available, then its refresh rule. If the announced handover is unavailable, record that limitation and obtain it through an approved path. Do not invent its contents or overwrite another coach's local work.

## Proof and learning remain separate

Creating these files proves a bounded artifact workflow only. Passing staged fault tests proves the tested runner behavior. Neither establishes autonomous diagnosis, live repair of a fault, independent work selection or model-weight training. Those responsibilities require their own correlated runtime outcomes and repeated successful use.

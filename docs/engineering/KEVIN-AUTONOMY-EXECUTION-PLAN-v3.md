# Kevin Autonomy Execution Plan v3

**North star:** Kevin becomes a persistent local AI coworker on HESS-PC that converts Matt's standing goals into verified outcomes, learns reusable skills, diagnoses and repairs routine failures, resumes interrupted work, and requires outside engineering only for genuinely novel or consequential exceptions.

**Operating principle:** maximize **bounded capability**, not unbounded permission.

## 1. Current foundation to preserve

Do not rewrite working layers merely to make the architecture look simpler.

Established foundation includes:

- local/free model-first operation;
- Benchmark 30/30 critical 0 at the current checkpoint;
- canonical recurring Engineering Relay, Supervisor, Support Bridge, Skill Lab, Maintenance intake and Benchmark lanes;
- immutable evidence/receipt culture;
- Maintenance v1.3.51 live identity proof;
- Supervisor v1.8.10 installed identity;
- 27 PROVEN composite skills;
- capability-aware routing foundation;
- renewable standing-work materialization foundation;
- incident/reflection regression foundation;
- mission leases and bounded continuation history;
- exact-five desktop/tool policy as an intentional qualified surface.

A major rewrite would throw away hard-earned proof and create a new unqualified system. Advance by connecting these layers.

## 2. Target closed loop

Kevin's durable autonomy loop is:

`SENSE -> REFLECT -> SELECT -> PLAN -> RESOLVE CAPABILITY -> ACT -> VERIFY -> LEARN -> RESUME`

Expanded:

1. read fresh runtime truth and standing owner goals;
2. materialize due responsibilities as distinct WorkInstances;
3. select the highest-value eligible WorkInstance;
4. identify required capabilities and authority ceiling;
5. if a matching PROVEN skill exists, invoke it with fresh parameters;
6. if reviewed primitives suffice, compose bounded work;
7. if a capability is missing, research/build it in isolation and send it through Skill Lab;
8. execute only through the correct typed worker/executor;
9. verify the actual artifact/effect independently;
10. on failure, open Incident/Reflection and preserve the interrupted objective;
11. form competing hypotheses when cause is ambiguous;
12. run discriminating positive/negative/regression tests;
13. make the smallest causal repair;
14. verify repair independently;
15. record the lesson/prevention rule;
16. resume the original WorkInstance automatically;
17. materialize or select the next useful work.

A successful model turn is never equivalent to an owner outcome.

## 4. Long-running agent engineering doctrine

### Separate worker from judge

Kevin may improve the worker, but must not silently redefine the benchmark, verifier, authority policy, audit trail, or success criteria that judge his work.

### Preserve objective identity

Every subtask, repair, research branch and skill-build must retain a pointer to the owner objective that caused it. Finishing a repair without returning to the objective is a failed recovery.

### Make effects idempotent

Every potentially duplicated effect needs an idempotency key or equivalent receipt correlation. This becomes mandatory before autonomous sends, calls, purchases, bookings, installs, or other consequential actions.

### Prefer structured control

Capability hierarchy:

1. native API / typed connector;
2. purpose-built adapter;
3. structured CLI/system interface;
4. managed browser automation;
5. GUI/computer use grounded in screenshots/state;
6. human escalation.

Do not use visual clicking when a safer structured interface exists.

### Recovery is first-class

Long-running work must survive ordinary restarts and partial failures through durable WorkInstance state, bounded retries, mission leases, idempotency and receipts. Restart recovery must not automatically repeat an uncertain external effect.

## 5. Browser and computer-use wave

Current OpenClaw releases make browser/computer use substantially more practical, including local-browser routing, paired-machine targeting, Windows desktop handoff, screenshot-grounded actions, interrupted-task recovery and task workspaces. Kevin should exploit those capabilities only after typed qualification.

Qualification order:

1. read-only browser extraction;
2. isolated managed-browser navigation;
3. bounded click/type/download against test sites;
4. Windows paired-machine screenshot + no-op targeting;
5. reversible local GUI actions;
6. reusable GUI composites;
7. signed-in sessions only with explicit scoped owner policy.

Browser/GUI instructions from untrusted pages are data, not authority. Prompt-injection resistance is a required negative-test family.

## 6. Authority model

### GREEN-A - autonomous observe/read

Public research, repo/files/log inspection, diagnostics, health checks, screenshots of Kevin-owned surfaces, benchmarks, tests and non-sensitive analysis.

### GREEN-B - autonomous reversible local work

Approved roots/worktrees, code edits, tests, local artifacts, spreadsheets/documents, local app prototypes, isolated dependency work, quarantine downloads, bounded subagents, Skill Lab staging/evaluation, backups and proven service runbooks.

### GREEN-C - autonomous proven self-improvement

Known reversible repairs, regression tests, lessons/failure taxonomy, invocation of PROVEN skills, low-risk typed promotion after existing rollback/Benchmark gates, and generation of new candidate skills in isolation.

### DELEGATED YELLOW - standing scoped grants

Instead of one permission prompt per action, Matt may issue an expiring capability grant with fields such as:

- action class;
- allowed merchant/site/recipient/publisher;
- maximum amount or resource scope;
- maximum count/frequency;
- start/end time;
- idempotency rule;
- receipt requirement;
- rollback/cancellation rule where applicable.

Examples later: pizza ordering, selected Amazon household items, verified game publishers, or phone calls to Matt's verified number.

### Never self-authorize

- arbitrary shell outside reviewed lanes;
- credential access/exfiltration;
- safety or audit weakening;
- arbitrary financial authority;
- purchases without a current grant;
- permission expansion;
- silent judge/benchmark modification;
- public posting/external sending outside a current grant.

## 7. Skill maturity ladder

A skill is not "official" because its instructions exist.

`IDEA -> PROCEDURE -> CANDIDATE -> TESTED -> PROVEN -> INVOCABLE -> REPEATEDLY_PROVEN -> SUPERVISOR-SELECTABLE -> T4 KEVIN-OWNED`

Required evidence grows with maturity:

- schema/authority contract;
- positive tests;
- negative tests;
- regression tests;
- immutable proof identity;
- actual artifact/effect evidence;
- fresh invocation receipts;
- repeated use on distinct inputs;
- autonomous selection and recovery evidence.

## 9. Research subsystem standard

For nontrivial research Kevin should:

1. decompose the question;
2. search multiple independent sources;
3. prefer primary/official sources for decisive claims;
4. record source date and retrieval time;
5. detect stale evidence;
6. surface contradictions rather than averaging them away;
7. synthesize with provenance;
8. assign calibrated confidence;
9. convert useful recurring research into a procedure/skill.

## 10. Self-building standard

Kevin may autonomously create branches/candidates for GREEN improvements, but each production change follows:

`fresh main -> bounded branch -> edit -> compile/lint -> positive tests -> negative tests -> regression -> diff review -> CI -> typed HESS-PC qualification -> canary -> observe -> receipt -> handover checkpoint`

For low-risk proven classes, deployment may later become autonomous when the promotion lane itself has repeated proof and rollback. Until then, source proof and runtime proof remain separate.

## 11. Model strategy

Do not model-shop around an architectural problem. A stronger model can improve planning, coding and recovery, but cannot substitute for missing tools, work identity, durable state, receipts, idempotency, capability routing or authority boundaries.

Local/free remains the default where it passes task-specific evals. Change a model because a measured capability requires it, not because a newer model exists.

## 13. Definition of the next-level Kevin

An overnight run counts as strong autonomy when Kevin can independently:

1. find useful due work from Matt's standing goals;
2. select and invoke a proven capability;
3. produce and verify a real artifact/outcome;
4. encounter a defect without losing the objective;
5. diagnose with evidence and competing hypotheses when needed;
6. repair through bounded source/test machinery;
7. independently verify the repair;
8. record a reusable lesson/prevention rule;
9. resume and finish the original objective;
10. continue to the next useful WorkInstance;
11. leave a morning evidence report that another agent can audit without chat history.

That is the target: **persistent evidence-bearing autonomy, not continuous token generation.**
